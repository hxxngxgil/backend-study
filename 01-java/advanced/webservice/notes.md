# HTTP Server Practical

## HTTP 서버 활용

이번 단원에서는 직접 만든 HTTP 서버에 애노테이션 기반 서블릿 구조를 적용하고,  
회원 관리 서비스까지 만들어보면서 HTTP 서버를 실제 웹 애플리케이션 서버처럼 확장하는 방법을 학습했다.

학습 흐름

1. 애노테이션 서블릿 시작
2. 동적 바인딩
3. 성능 최적화
4. 회원 관리 서비스

---

# HTTP 서버 - 애노테이션 서블릿 시작

기존 HTTP 서버는 요청 URL에 따라 직접 if문이나 Map으로 요청을 분기했다.

예시

/hello 요청

/site1 요청

/site2 요청

이 방식도 동작은 하지만, 요청이 많아질수록 관리가 어려워진다.

---

## 기존 방식의 문제점

- URL이 늘어날수록 코드가 복잡해진다.
- 요청 처리 코드가 한 곳에 모이기 쉽다.
- 새로운 기능을 추가할 때 기존 코드를 수정해야 한다.
- 유지보수가 어려워진다.

---

## 애노테이션 기반 서블릿

애노테이션 기반 서블릿은 메서드에 애노테이션을 붙여서  
특정 URL 요청을 처리하도록 만드는 방식이다.

예시

@Mapping("/hello")
public void hello(HttpRequest request, HttpResponse response) {
    response.writeBody("<h1>Hello</h1>");
}

---

## 애노테이션 기반 방식의 장점

- URL과 처리 메서드를 가까운 곳에 둘 수 있다.
- 요청 처리 코드가 메서드 단위로 분리된다.
- 새로운 URL 기능을 추가하기 쉽다.
- 코드 구조가 깔끔해진다.

---

# HTTP 서버 - 애노테이션 서블릿 동작 흐름

애노테이션 기반 HTTP 서버는 다음 흐름으로 동작한다.

1. 클라이언트가 HTTP 요청을 보낸다.
2. 서버가 요청 경로를 분석한다.
3. 컨트롤러 객체들을 탐색한다.
4. 각 컨트롤러의 메서드들을 리플렉션으로 확인한다.
5. @Mapping 애노테이션이 있는 메서드를 찾는다.
6. 애노테이션의 URL 값과 요청 경로를 비교한다.
7. 일치하면 해당 메서드를 동적으로 호출한다.
8. 응답 객체를 통해 HTTP 응답을 반환한다.

---

# 리플렉션과 애노테이션 활용

애노테이션 기반 서블릿은 리플렉션과 애노테이션을 함께 사용한다.

애노테이션 역할

- URL 매핑 정보를 표시한다.
- 어떤 메서드가 어떤 요청을 처리하는지 알려준다.

리플렉션 역할

- 런타임에 클래스와 메서드 정보를 조회한다.
- @Mapping 애노테이션이 붙은 메서드를 찾는다.
- 해당 메서드를 동적으로 호출한다.

---

## 예시 흐름

요청

GET /site1 HTTP/1.1

컨트롤러 메서드

@Mapping("/site1")
public void site1(HttpRequest request, HttpResponse response) {
    response.writeBody("<h1>site1</h1>");
}

처리 흐름

1. request.getPath()로 "/site1" 추출
2. 컨트롤러 목록 탐색
3. getDeclaredMethods()로 메서드 목록 조회
4. @Mapping 애노테이션 확인
5. mapping.value()와 request path 비교
6. 일치하면 method.invoke()로 호출

---

# HTTP 서버 - 동적 바인딩

동적 바인딩은 실행 시점에 어떤 메서드를 호출할지 결정하는 것이다.

일반적인 메서드 호출은 컴파일 시점에 호출 대상이 정해진다.

예시

controller.site1(request, response);

하지만 애노테이션 기반 서버에서는 요청 URL에 따라  
실행 시점에 호출할 메서드가 결정된다.

예시

method.invoke(controller, request, response);

---

## 동적 바인딩이 필요한 이유

클라이언트가 어떤 URL로 요청할지는 실행 전에는 알 수 없다.

따라서 서버는 실행 중에 요청 경로를 확인하고  
그 경로에 맞는 메서드를 찾아 호출해야 한다.

---

## 동적 바인딩의 장점

- 요청 URL에 따라 실행할 메서드를 유연하게 선택할 수 있다.
- 새로운 URL 처리 메서드를 추가해도 서버 핵심 코드를 크게 수정하지 않아도 된다.
- 프레임워크처럼 동작하는 구조를 만들 수 있다.

---

# HTTP 서버 - 성능 최적화

처음 구현한 애노테이션 기반 서버는 요청이 올 때마다  
컨트롤러와 메서드를 계속 탐색할 수 있다.

이 방식은 동작은 하지만 성능이 좋지 않을 수 있다.

---

## 기존 방식의 문제점

요청마다 반복되는 작업

- 컨트롤러 목록 탐색
- 메서드 목록 조회
- 애노테이션 확인
- URL 비교

요청이 많아질수록 같은 탐색 작업이 반복된다.

---

## 성능 최적화 방법

서버 시작 시점에 미리 URL과 메서드 정보를 찾아서 저장해둔다.

즉, 요청이 들어올 때마다 탐색하지 않고  
미리 만들어둔 매핑 정보를 사용한다.

---

## 매핑 정보 캐싱

서버 시작 시 다음 정보를 미리 저장한다.

- URL 경로
- 컨트롤러 객체
- 실행할 메서드

예시

/hello → HelloController.hello()

/site1 → SiteController.site1()

/site2 → SiteController.site2()

---

## 성능 최적화 후 요청 처리 흐름

1. 서버 시작 시 @Mapping 메서드를 미리 탐색한다.
2. URL과 실행 메서드를 Map에 저장한다.
3. 요청이 들어오면 request path를 확인한다.
4. Map에서 path에 맞는 메서드를 바로 찾는다.
5. 해당 메서드를 실행한다.

---

## 성능 최적화 장점

- 요청마다 리플렉션 탐색을 반복하지 않아도 된다.
- URL 매핑 조회가 빨라진다.
- 코드 구조가 더 명확해진다.
- 서버가 요청을 더 효율적으로 처리할 수 있다.

---

# HTTP 서버 활용 - 회원 관리 서비스

애노테이션 기반 HTTP 서버를 활용해서  
간단한 회원 관리 서비스를 만들 수 있다.

예시 기능

- 회원 등록
- 회원 목록 조회
- 회원 상세 조회
- 회원 검색

---

## 회원 관리 서비스 흐름

1. 클라이언트가 회원 관련 URL로 요청한다.
2. HTTP 서버가 요청 경로를 분석한다.
3. @Mapping 정보와 매칭되는 메서드를 찾는다.
4. 컨트롤러 메서드가 실행된다.
5. 서비스 또는 저장소를 사용해서 회원 데이터를 처리한다.
6. HTTP 응답으로 결과 HTML 또는 텍스트를 반환한다.

---

## 예시 URL

회원 목록

/members

회원 등록 폼

/members/new-form

회원 저장

/members/save

회원 검색

/members/search

---

# 구성 역할과 사용 역할

이번 단원에서는 객체의 역할을 크게 구성 역할과 사용 역할로 나눠서 이해할 수 있다.

---

## 구성 역할

구성 역할은 애플리케이션이 실행될 때 필요한 객체들을 만들고 연결하는 역할이다.

예시

- 컨트롤러 생성
- 서비스 생성
- 저장소 생성
- URL과 메서드 매핑
- 필요한 의존관계 연결

구성 역할은 애플리케이션의 전체 구조를 조립하는 역할이다.

---

## 사용 역할

사용 역할은 이미 구성된 객체들을 실제 요청 처리에 사용하는 역할이다.

예시

- HTTP 요청 처리
- 컨트롤러 메서드 실행
- 회원 저장
- 회원 조회
- HTTP 응답 생성

사용 역할은 실제 비즈니스 동작을 수행하는 역할이다.

---

## 구성 역할과 사용 역할을 나누는 이유

객체를 만들고 연결하는 코드와  
실제로 사용하는 코드를 분리하기 위해서이다.

이렇게 분리하면 코드가 더 깔끔해지고 유지보수하기 쉬워진다.

---

# 구성 역할과 사용 역할 분리의 장점

## 유연성 향상

구현체를 쉽게 교체할 수 있다.

예를 들어 회원 저장소를 메모리 저장소에서 파일 저장소나 DB 저장소로 변경하더라도  
사용하는 쪽의 코드를 크게 바꾸지 않을 수 있다.

---

## 테스트 용이성

구성 역할과 사용 역할이 분리되어 있으면 테스트가 쉬워진다.

예를 들어 실제 저장소 대신 테스트용 저장소를 주입해서  
회원 관리 기능만 따로 테스트할 수 있다.

---

## 코드 재사용성 증가

공통으로 필요한 객체나 설정을 한 곳에서 구성하면  
여러 곳에서 같은 객체를 재사용할 수 있다.

중복 생성이나 중복 설정을 줄일 수 있다.

---

## 관심사의 분리

객체를 생성하고 연결하는 관심사와  
실제 기능을 실행하는 관심사를 분리할 수 있다.

예시

구성 관심사

- 어떤 컨트롤러를 사용할지
- 어떤 저장소를 사용할지
- 어떤 URL과 메서드를 연결할지

사용 관심사

- 요청을 어떻게 처리할지
- 회원을 어떻게 저장할지
- 응답을 어떻게 만들지

---

## 유지보수 용이성

객체 생성과 연결 구조가 한 곳에 모여 있으면  
변경이 발생했을 때 수정할 위치를 찾기 쉽다.

기능 코드와 구성 코드가 섞여 있는 것보다  
수정 범위가 줄어든다.

---

## 확장성 개선

새로운 기능을 추가할 때 기존 코드를 크게 건드리지 않고  
새로운 컨트롤러나 메서드를 추가할 수 있다.

애노테이션 기반 매핑 구조를 사용하면  
새로운 URL을 추가하는 작업도 쉬워진다.

---

# 애노테이션 서블릿 구조의 장점

애노테이션 서블릿 구조는 직접 만든 HTTP 서버를  
프레임워크처럼 동작하게 만든다.

장점

- URL 매핑을 애노테이션으로 표현할 수 있다.
- 컨트롤러 메서드를 자동으로 탐색할 수 있다.
- 동적 바인딩으로 요청에 맞는 메서드를 실행할 수 있다.
- 성능 최적화를 통해 매핑 정보를 미리 캐싱할 수 있다.
- 기능 추가 시 기존 서버 코드를 덜 수정할 수 있다.

---

# 스프링 MVC와의 연결

이번 단원에서 만든 구조는 스프링 MVC의 핵심 흐름과 비슷하다.

스프링 MVC에서도

- @Controller
- @RequestMapping
- @GetMapping
- @PostMapping

같은 애노테이션을 사용해서  
요청 URL과 컨트롤러 메서드를 연결한다.

---

## 직접 만든 서버와 스프링 MVC 비교

직접 만든 HTTP 서버

- @Mapping 애노테이션으로 URL 매핑
- 리플렉션으로 메서드 탐색
- method.invoke()로 메서드 실행
- 직접 HttpRequest, HttpResponse 생성

스프링 MVC

- @RequestMapping, @GetMapping 등으로 URL 매핑
- 스프링이 컨트롤러와 메서드 탐색
- 스프링이 파라미터 바인딩과 메서드 호출 처리
- 스프링이 요청과 응답 객체 관리

---

# 핵심 정리

1. 애노테이션 기반 서블릿은 URL과 메서드를 애노테이션으로 연결한다.
2. 리플렉션을 사용하면 런타임에 @Mapping 메서드를 찾아 실행할 수 있다.
3. 동적 바인딩은 실행 시점에 호출할 메서드를 결정하는 것이다.
4. 요청마다 리플렉션 탐색을 반복하면 성능이 떨어질 수 있다.
5. 서버 시작 시점에 URL과 메서드 정보를 미리 캐싱하면 성능을 개선할 수 있다.
6. 회원 관리 서비스 예제를 통해 직접 만든 HTTP 서버를 실제 서비스처럼 활용할 수 있다.
7. 구성 역할은 객체를 생성하고 연결하는 역할이다.
8. 사용 역할은 이미 구성된 객체를 사용해서 실제 기능을 수행하는 역할이다.
9. 구성 역할과 사용 역할을 분리하면 유연성이 향상된다.
10. 테스트 용이성, 코드 재사용성, 관심사의 분리, 유지보수성, 확장성이 좋아진다.
11. 이번 구조는 스프링 MVC의 @RequestMapping 기반 요청 처리 구조를 이해하는 데 도움이 된다.
