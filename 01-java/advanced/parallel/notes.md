# 단일 스트림

## 단일 스트림이란?

단일 스트림은 하나의 스레드에서 데이터를 순차적으로 처리하는 방식이다.

일반적인 stream()은 기본적으로 단일 스레드에서 동작한다.

예시

List<Integer> result = numbers.stream()
        .map(number -> number * 2)
        .toList();

---

## 단일 스트림의 특징

- 하나의 스레드에서 순서대로 처리한다.
- 코드 흐름이 단순하다.
- 디버깅이 쉽다.
- 동시성 문제가 거의 없다.
- 데이터 양이 적거나 작업이 가벼우면 충분히 빠르다.

---

## 단일 스트림의 한계

처리해야 할 데이터가 많고  
각 작업의 계산 비용이 크다면 하나의 스레드만으로는 시간이 오래 걸릴 수 있다.

이런 경우 여러 스레드로 작업을 나누어 병렬 처리하는 방법을 고려할 수 있다.

---

# 스레드 직접 사용

## 직접 스레드 사용

자바에서는 Thread를 직접 생성해서 작업을 병렬로 처리할 수 있다.

예시

Thread thread1 = new Thread(() -> task1());

Thread thread2 = new Thread(() -> task2());

thread1.start();

thread2.start();

---

## 직접 스레드 사용의 장점

- 병렬 처리를 직접 구현할 수 있다.
- 작업을 여러 스레드에 나누어 실행할 수 있다.
- 간단한 예제에서는 이해하기 쉽다.

---

## 직접 스레드 사용의 단점

- 스레드 생성과 종료 비용이 크다.
- 스레드 개수를 직접 관리해야 한다.
- 작업 분배가 어렵다.
- 결과를 모으는 코드가 복잡해질 수 있다.
- 예외 처리와 자원 관리가 어렵다.

---

# 스레드 풀 사용

## 스레드 풀이란?

스레드 풀은 미리 여러 개의 스레드를 만들어두고  
작업이 들어오면 기존 스레드를 재사용하는 방식이다.

자바에서는 ExecutorService를 사용해서 스레드 풀을 만들 수 있다.

---

## 스레드 풀 예시

ExecutorService executor = Executors.newFixedThreadPool(4);

executor.submit(() -> task1());

executor.submit(() -> task2());

executor.shutdown();

---

## 스레드 풀의 장점

- 스레드를 매번 새로 만들지 않아도 된다.
- 스레드 생성 비용을 줄일 수 있다.
- 동시에 실행할 스레드 수를 제한할 수 있다.
- 많은 작업을 효율적으로 처리할 수 있다.

---

## 스레드 풀의 한계

스레드 풀을 사용해도 작업을 어떻게 나눌지 직접 결정해야 한다.

예를 들어 큰 리스트를 여러 구간으로 나누고,  
각 구간의 결과를 계산하고,  
다시 하나의 결과로 합치는 코드를 작성해야 한다.

이런 작업 분할과 결과 병합을 편하게 지원하기 위해 Fork/Join 방식이 등장한다.

---

# Fork/Join 패턴

## Fork/Join이란?

Fork/Join은 큰 작업을 작은 작업으로 나누고,  
작은 작업을 병렬로 처리한 뒤,  
결과를 다시 합치는 방식이다.

Fork

작업을 나눈다.

Join

나눈 작업의 결과를 합친다.

---

## Fork/Join 패턴 흐름

1. 큰 작업을 작은 작업으로 분할한다.
2. 작은 작업을 여러 스레드에서 병렬로 실행한다.
3. 더 이상 나눌 필요가 없을 정도로 작아지면 직접 계산한다.
4. 계산된 결과들을 다시 합친다.
5. 최종 결과를 반환한다.

---

## Fork/Join 예시 개념

1부터 100까지 합계를 구한다고 가정한다.

작업 분할

1 ~ 100

→ 1 ~ 50

→ 51 ~ 100

각 작업을 병렬로 계산한 뒤 결과를 합친다.

결과

sum(1 ~ 50) + sum(51 ~ 100)

---

# Fork/Join 프레임워크 - 소개

## Fork/Join 프레임워크란?

Fork/Join 프레임워크는 자바에서 Fork/Join 패턴을 쉽게 구현할 수 있도록 제공하는 프레임워크이다.

큰 작업을 작은 작업으로 나누고  
여러 스레드에서 병렬로 처리한 뒤  
결과를 합치는 구조를 지원한다.

---

## 주요 클래스

ForkJoinPool

- Fork/Join 작업을 실행하는 스레드 풀이다.
- 여러 워커 스레드를 관리한다.

RecursiveTask

- 결과를 반환하는 작업을 만들 때 사용한다.

RecursiveAction

- 결과를 반환하지 않는 작업을 만들 때 사용한다.

---

## RecursiveTask 예시 흐름

class SumTask extends RecursiveTask<Long> {

    @Override
    protected Long compute() {
        if (작업이 충분히 작으면) {
            return 직접 계산;
        }

        SumTask leftTask = new SumTask(...);
        SumTask rightTask = new SumTask(...);

        leftTask.fork();

        Long rightResult = rightTask.compute();

        Long leftResult = leftTask.join();

        return leftResult + rightResult;
    }
}

---

## Fork/Join 프레임워크의 장점

- 큰 작업을 작은 작업으로 나누기 쉽다.
- 병렬 처리 구조를 만들 수 있다.
- 스레드 풀을 직접 세밀하게 관리하지 않아도 된다.
- 작업 훔치기 알고리즘을 통해 스레드를 효율적으로 사용할 수 있다.

---

# Fork/Join 프레임워크 - 작업 훔치기

## 작업 훔치기란?

작업 훔치기는 일이 없는 스레드가  
다른 바쁜 스레드의 작업 큐에서 남은 작업을 가져와 처리하는 방식이다.

영어로는 Work Stealing이라고 한다.

---

## 작업 훔치기가 필요한 이유

병렬 처리에서는 모든 스레드가 항상 같은 양의 일을 가지지 않는다.

어떤 스레드는 작업이 빨리 끝날 수 있고,  
어떤 스레드는 아직 많은 작업을 가지고 있을 수 있다.

이때 빨리 끝난 스레드가 그냥 놀고 있으면 자원이 낭비된다.

작업 훔치기를 사용하면  
일이 없는 스레드가 다른 스레드의 작업을 가져와 처리해서  
전체 작업 시간을 줄일 수 있다.

---

# 작업 훔치기 알고리즘

## 기본 구조

Fork/Join 프레임워크의 각 워커 스레드는 자신의 작업 큐를 가진다.

자신의 작업 큐에 작업이 있으면 직접 처리한다.

자신의 작업이 모두 끝나면  
다른 워커 스레드의 작업 큐에서 작업을 가져와 처리한다.

---

## 작업 훔치기 흐름

1. 큰 작업이 작은 작업으로 나뉜다.
2. 나뉜 작업들이 각 워커 스레드의 큐에 들어간다.
3. 각 스레드는 자신의 큐에 있는 작업을 처리한다.
4. 어떤 스레드가 자신의 작업을 모두 끝낸다.
5. 일이 없는 스레드는 다른 스레드의 큐를 확인한다.
6. 다른 스레드의 남은 작업을 훔쳐와서 처리한다.
7. 모든 작업이 끝나면 결과를 합친다.

---

## 작업 훔치기의 장점

- 스레드가 놀고 있는 시간을 줄일 수 있다.
- 작업량이 균등하지 않아도 효율적으로 처리할 수 있다.
- CPU 자원을 더 잘 활용할 수 있다.
- 병렬 처리 성능을 높일 수 있다.

---

# Fork/Join 프레임워크 - 공용 풀

## 공용 풀이란?

자바는 Fork/Join 프레임워크를 위한 공용 풀을 제공한다.

공용 풀은 애플리케이션 전체에서 공유되는 ForkJoinPool이다.

병렬 스트림도 기본적으로 이 공용 풀을 사용한다.

---

## 공용 풀 확인

ForkJoinPool commonPool = ForkJoinPool.commonPool();

---

## 공용 풀의 특징

- 애플리케이션 전역에서 공유된다.
- 별도로 풀을 만들지 않아도 사용할 수 있다.
- 병렬 스트림이 기본적으로 사용한다.
- CPU 코어 수를 기준으로 병렬 처리를 수행한다.

---

## 공용 풀 사용 시 주의점

공용 풀은 여러 곳에서 함께 사용할 수 있다.

따라서 한 곳에서 오래 걸리는 작업이나 블로킹 작업을 많이 실행하면  
다른 병렬 작업에도 영향을 줄 수 있다.

예시

- 오래 걸리는 파일 I/O
- DB 호출
- 네트워크 호출
- Thread.sleep()
- 외부 API 호출

이런 작업은 공용 풀을 오래 점유할 수 있으므로 주의해야 한다.

---

# 자바 병렬 스트림

## 병렬 스트림이란?

병렬 스트림은 Stream API의 데이터를 여러 스레드에서 나누어 처리하는 방식이다.

기존 stream()은 기본적으로 순차 처리한다.

parallelStream()을 사용하면 병렬 처리가 가능하다.

---

## 병렬 스트림 사용 방법

컬렉션에서 바로 사용

List<Integer> result = numbers.parallelStream()
        .map(number -> number * 2)
        .toList();

기존 스트림을 병렬로 변경

List<Integer> result = numbers.stream()
        .parallel()
        .map(number -> number * 2)
        .toList();

---

## 병렬 스트림의 동작 방식

병렬 스트림은 내부적으로 데이터를 여러 조각으로 나눈다.

그리고 Fork/Join 프레임워크와 공용 풀을 사용해서  
여러 스레드가 동시에 작업을 처리한다.

처리가 끝나면 나누어진 결과를 다시 합친다.

---

## 병렬 스트림이 유리한 경우

- 데이터 양이 많다.
- 각 요소를 처리하는 연산 비용이 크다.
- 작업이 독립적이다.
- 공유 자원을 변경하지 않는다.
- CPU 중심의 계산 작업이다.
- 결과 순서가 크게 중요하지 않다.

---

## 병렬 스트림이 불리한 경우

- 데이터 양이 적다.
- 각 요소 처리 비용이 작다.
- 작업을 나누고 합치는 비용이 더 크다.
- 공유 가변 상태를 변경한다.
- DB, 파일, 네트워크 같은 블로킹 I/O 작업이 많다.
- 순서 보장이 중요하다.

---

# 병렬 스트림 사용 시 주의점

## 1. 무조건 빠른 것은 아니다

병렬 스트림은 여러 스레드를 사용하므로 항상 빠를 것 같지만 그렇지 않다.

작업을 나누고, 스레드에서 실행하고, 결과를 합치는 비용이 발생한다.

데이터가 적거나 연산이 단순하면  
오히려 단일 스트림보다 느릴 수 있다.

---

## 2. 공유 가변 상태를 변경하면 위험하다

병렬 스트림에서는 여러 스레드가 동시에 작업한다.

이때 같은 변수를 동시에 변경하면 데이터가 꼬일 수 있다.

나쁜 예시

List<Integer> result = new ArrayList<>();

numbers.parallelStream()
        .forEach(number -> result.add(number));

문제점

ArrayList는 여러 스레드가 동시에 add()를 호출하는 상황에 안전하지 않다.

---

## 3. collect를 사용해서 결과를 모으는 것이 좋다

병렬 스트림에서는 외부 리스트를 직접 변경하기보다  
스트림의 collect나 toList를 사용해서 결과를 모으는 것이 좋다.

좋은 예시

List<Integer> result = numbers.parallelStream()
        .map(number -> number * 2)
        .toList();

---

## 4. 순서가 보장되지 않을 수 있다

parallelStream()에서 forEach()를 사용하면 처리 순서가 보장되지 않을 수 있다.

예시

numbers.parallelStream()
        .forEach(System.out::println);

순서가 중요하다면 forEachOrdered()를 사용할 수 있다.

예시

numbers.parallelStream()
        .forEachOrdered(System.out::println);

주의

순서를 보장하면 병렬 처리 성능 이점이 줄어들 수 있다.

---

## 5. 블로킹 작업에 주의한다

병렬 스트림은 기본적으로 ForkJoinPool의 공용 풀을 사용한다.

DB 조회, 파일 I/O, 네트워크 호출처럼 오래 기다리는 작업을 병렬 스트림으로 처리하면  
공용 풀의 스레드가 막힐 수 있다.

그러면 다른 병렬 작업에도 영향을 줄 수 있다.

---

## 6. 작업이 독립적이어야 한다

병렬 스트림에 전달하는 람다는 가능한 한 순수 함수에 가까워야 한다.

즉, 같은 입력에 같은 결과를 반환하고  
외부 상태를 변경하지 않는 것이 좋다.

좋은 예시

numbers.parallelStream()
        .map(number -> number * 2)
        .toList();

나쁜 예시

int[] sum = {0};

numbers.parallelStream()
        .forEach(number -> sum[0] += number);

---

## 7. 성능 측정 후 사용한다

병렬 스트림은 상황에 따라 성능이 좋아질 수도 있고 나빠질 수도 있다.

따라서 병렬 스트림을 사용하기 전후로  
실제 데이터와 실제 환경에서 성능을 측정해보는 것이 좋다.

---

# 단일 스트림과 병렬 스트림 비교

| 구분 | 단일 스트림 | 병렬 스트림 |
|------|-------------|-------------|
| 실행 방식 | 하나의 스레드에서 순차 처리 | 여러 스레드에서 병렬 처리 |
| 사용 메서드 | stream() | parallelStream(), parallel() |
| 장점 | 단순함, 안정적, 디버깅 쉬움 | CPU를 활용한 성능 향상 가능 |
| 단점 | 큰 계산 작업은 느릴 수 있음 | 오버헤드, 동시성 문제 가능 |
| 적합한 작업 | 일반적인 데이터 처리 | 큰 데이터 + 무거운 CPU 계산 |
| 주의점 | 특별한 동시성 이슈 적음 | 공유 상태, 순서, 공용 풀 주의 |

---

# stream(), parallelStream(), parallel()

## stream()

컬렉션 데이터를 순차 스트림으로 처리한다.

예시

numbers.stream()

---

## parallelStream()

컬렉션 데이터를 바로 병렬 스트림으로 처리한다.

예시

numbers.parallelStream()

---

## parallel()

이미 생성된 스트림을 병렬 스트림으로 전환한다.

예시

numbers.stream()
        .parallel()
        .map(number -> number * 2)
        .toList();

---

# 병렬 스트림과 함수형 프로그래밍

병렬 스트림은 함수형 프로그래밍의 장점과 잘 맞는다.

함수형 프로그래밍은 다음을 중요하게 생각한다.

- 순수 함수
- 불변성
- 부수 효과 최소화

병렬 처리에서는 여러 스레드가 동시에 작업하기 때문에  
공유 상태 변경이 적을수록 안전하다.

따라서 병렬 스트림에서는  
외부 상태를 변경하지 않는 람다를 사용하는 것이 중요하다.

---

# 핵심 정리

1. 단일 스트림은 하나의 스레드에서 데이터를 순차적으로 처리한다.
2. 스레드를 직접 사용하면 병렬 처리를 구현할 수 있지만 관리가 어렵다.
3. 스레드 풀은 스레드를 재사용해서 생성 비용을 줄인다.
4. Fork/Join 패턴은 큰 작업을 작은 작업으로 나누고 결과를 합치는 방식이다.
5. Fork는 작업을 나누는 것이고 Join은 결과를 합치는 것이다.
6. Fork/Join 프레임워크는 Fork/Join 패턴을 자바에서 쉽게 구현하도록 지원한다.
7. RecursiveTask는 결과가 있는 작업에 사용한다.
8. RecursiveAction은 결과가 없는 작업에 사용한다.
9. 작업 훔치기는 일이 없는 스레드가 다른 스레드의 작업을 가져와 처리하는 방식이다.
10. 작업 훔치기를 사용하면 스레드가 놀고 있는 시간을 줄일 수 있다.
11. ForkJoinPool.commonPool()은 애플리케이션 전역에서 공유되는 공용 풀이다.
12. 병렬 스트림은 내부적으로 Fork/Join 프레임워크와 공용 풀을 사용한다.
13. parallelStream() 또는 parallel()을 사용하면 병렬 스트림을 만들 수 있다.
14. 병렬 스트림은 데이터 양이 많고 CPU 계산 비용이 큰 작업에 유리할 수 있다.
15. 데이터가 적거나 작업이 가벼우면 병렬 스트림이 오히려 느릴 수 있다.
16. 병렬 스트림에서는 공유 가변 상태를 변경하면 동시성 문제가 발생할 수 있다.
17. 외부 리스트에 직접 add()하기보다 toList()나 collect()를 사용하는 것이 좋다.
18. 병렬 스트림의 forEach()는 순서가 보장되지 않을 수 있다.
19. 순서가 중요하면 forEachOrdered()를 사용할 수 있지만 성능 이점이 줄어들 수 있다.
20. 병렬 스트림은 공용 풀을 사용하므로 블로킹 I/O 작업에는 주의해야 한다.
21. 병렬 스트림은 무조건 빠른 것이 아니므로 실제 성능 측정 후 사용하는 것이 좋다.
